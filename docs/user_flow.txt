User Journey for the Requisition Platform
This user journey outlines the step-by-step flow for a requisition request, from initiation by a staff member to final payment and delivery confirmation.


Requisition Portal User Flow (Updated)
This flow covers request creation, item-level approval, RFQ generation, PO approval, delivery confirmation with GRN, and payment completion. All users can create requests. Each Request, RFQ, and PO has an autogenerated number and supports seamless navigation between linked artifacts.
1. Request Creation (All Staff as Requesters)
	•Start: User logs in via intranet and opens New Request.
	•Request header fields: Request Title, Urgency, Justification, Delivery Date, Delivery Location.
	•Items are mandatory: At least one item must be added via an Add Item pop-up
	•Add Item pop-up fields: Item Name, Description, Quantity, Brand, Unit of Measure (UOM), Unit Price (optional/estimated), Amount (auto-calculated), Working Tool toggle.
	•Multiple locations: If needed in multiple locations, add separate items per location.
	•Edits: Requester can edit request and items until HOD approval is recorded.
Outputs:
	•Request Number generated; status = Draft → Submitted after save and submit.
2. HOD Item-Level Approval
	•HOD receives notification of new submitted request.
	•HOD dashboard shows all department requests with filters; request detail shows items grid.
	•Approve per item: HOD can approve/deny individual items and comment at request or item level.
	•Bulk actions: Checkbox at top to select multiple items → Approve selected / Delete selected.
	•Routing rule: If a request has any item marked Working Tool, it is  routed to HR first; before going to the PM.
Outputs:
	•Item statuses transition: Pending → HOD Approved / HOD Rejected.
3. HR Review for Working Tools
	•Items flagged as Working Tools go to HR for approval before PM.
	•HR can approve/deny and comment per item; bulk approve where applicable
	•Approved working-tool items then proceed to PM.
Outputs:
	•HR approval stamps recorded in item history.
4. Procurement Intake (PM)
	•PM dashboard lists all items approved by HOD/HR, grouped by request.
	•PM cannot edit the original request header or item history to preserve audit trail.
	•PM can start RFQ generation from a request detail via “Generate RFQ” CTA.
Outputs:
	•Traceability links: Request ↔ RFQs; later RFQs ↔ POs.
5. RFQ Generation and Management
Within a request, PM clicks Generate RFQ and proceeds:
	•Select items: PM chooses one or more approved items to include in the RFQ.
	•RFQ form prefilled:
	•RFQ Title (from Request Title)
	•Vendors (multi-select from Vendor Master; option to add new vendor quickly)
	•Items table shows:
	•Item Description (Item Name + Brand)
	•Detailed Specification (from Description)
	•UOM
	•Quantity
	•Expected Delivery Date
	•Evaluation Criteria (PM input)
	•Delivery Location (from request)
	•Terms and Conditions (PM input)
	•PM may edit any prefilled values before generating.
	•On generate: RFQs are created per vendor with unique RFQ Numbers.
	•RFQ list view: Shows all RFQs for the request, listed per vendor; PM can download one or multiple RFQs.
	•The PM sends the downloaded RFQs to the vendors outside the platform and negotiates to choose the vendor for each RFQ
Outputs:
	•RFQ records with status = Issued;
	•Request status changes to Vendor Bidding
6. PO Creation and Approval
	•PO is generated from the RFQ of the selected vendor. The PM uploads the quote from the vendor and; can bundle multiple items from the RFQ.
	•PO form (prefilled from RFQ, editable by PM)
	•Vendor (from RFQ, editable)
	•Delivery Location
	•Delivery Date
	•Items table: Item Description, Quantity, UOM, Brand, Unit Price;
	•The total Amount (calculated on the item table based on the items)
	•General Terms
	•Delivery Contact (staff dropdown)
	•Shipping (dropdown)
	•PM confirms and submits PO for approval; status updates (e.g., Draft → Submitted).
	•PO approval chain: Head of Finance (HoF) → Head of HR (HHR). Both can fill optional feedback whenever they are approving. After both approvals, PM can download and send to vendor; PM cannot edit or download during approval.
	•PO history viewable; PO has its own autogenerated PO Number with links back to RFQ and Request.
Outputs:
	•Approved PO ready for dispatch; audit trail intact.
	•Request status changes to Vendor Assigned
	•RFQ status changes to Vendor Assigned
	•PO status changes: Submitted → HoF Approved → Approved
7. Delivery and Good Receive Note (GRN)
	•Upon delivery, the GRN process verifies items received against PO: item identity, quantity, condition; capture signatures and timestamps. Final confirmation by requester.
	•The store manager can generate a GRN from the PO. He selects the items that have been delivered from the PO, adds remarks and then chooses the approving user. This defaults to the person that filled out the request, but can be edited. This would be a list of staff ont he platform. He can also edit the quantity of the items that has been delivered before submitting the GRN. Once done, he clicks the Received CTA to confirm delivery.
	•The receiving user also confirms what the store manager has sent and then the PM does the final confirmation.
Outputs:
	•GRN record stored and linked to PO and Request.
	•Request status changes to Delivered (or Partially Delivered if not all approved items have been delivered). Item statuses change to Delivered
	•RFQ status changes to Completed
	•PO status changes: Completed
	•GRN status changes to Delivered
